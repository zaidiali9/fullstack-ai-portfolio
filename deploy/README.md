# Deploying on Railway

Three apps are live on Railway's free plan (the plan allows one Postgres plus three services):

| App | URL |
|---|---|
| Cairn (kb-chat) | https://kb-chat-production-15ef.up.railway.app |
| Bookwell (booking) | https://booking-production-d564.up.railway.app |
| Tally (nl-analytics) | https://nl-analytics-production.up.railway.app |

Tidal Desk (helpdesk) and Fernwood Supply (storefront) deploy the same way but need a paid plan or a second free
project. All data is seed data; demo logins are in each app's README.

**AI is off in this deployment.** No provider key is set, so AI features say "AI unavailable" and Cairn answers from
keyword search only. To turn AI on, add `GROQ_API_KEY` or `GEMINI_API_KEY` (free tiers) to a service's variables in
the Railway dashboard. The service redeploys and picks the provider automatically (`packages/ai/src/config.ts`).

## Layout
- **One Postgres service** (Railway template, `postgres-ssl:18`, which includes `vector` and `btree_gist`) with
  one database per app: `kb_chat`, `booking`, `nl_analytics`.
- **One service per app**, built from the repo root with the app's own Dockerfile (standalone Next.js output):

| Variable | Value |
|---|---|
| `RAILWAY_DOCKERFILE_PATH` | `apps/<app>/Dockerfile` |
| `DATABASE_URL` | `postgresql://${{Postgres.PGUSER}}:${{Postgres.PGPASSWORD}}@${{Postgres.RAILWAY_PRIVATE_DOMAIN}}:5432/<db>` |
| `BETTER_AUTH_SECRET` | `${{secret(48)}}` (generated by Railway, never in the repo) |
| `APP_URL` | `https://${{RAILWAY_PUBLIC_DOMAIN}}` |
| `PORT` | `3000` |
| `CRON_SECRET` (kb-chat only) | `${{secret(32)}}` |

Generate the public domain (`railway domain --service <app>`) **before** the first deploy, so `APP_URL` resolves.

## Creating the databases (one-off setup job)
The Postgres service has no public TCP proxy, so migrations and seeds run **inside** Railway on the private network.
`deploy/Dockerfile.setup` runs `scripts/railway-setup.mjs`, which:
1. creates each app's database if it is missing, and prints the Postgres version and available extensions;
2. runs each app's `npm run setup` (migrations, then seed data) against its own database.

It prints no connection strings. With no free service slot left, the job temporarily borrowed the booking service:
```bash
railway variable set RAILWAY_DOCKERFILE_PATH=deploy/Dockerfile.setup --service booking
# plus ADMIN_DATABASE_URL=${{Postgres.DATABASE_URL}}, KB_CHAT_DATABASE_URL / BOOKING_DATABASE_URL /
# NL_ANALYTICS_DATABASE_URL (as in the table above), SETUP_APPS=kb-chat,booking,nl-analytics
railway up --service booking --ci
railway logs --service booking   # ends with "[setup] all done"
```
Then delete those five variables, set `RAILWAY_DOCKERFILE_PATH=apps/booking/Dockerfile` again and deploy each app:
```bash
railway up --service booking --ci
```
On a paid plan, use a separate `setup` service instead and delete it afterwards. Seeds reset demo data, so re-running the
job is also how to restore a demo that visitors have changed.

## Notes
- The Railway CLI must run from PowerShell on this machine (see DECISIONS.md).
- `.railwayignore` keeps `node_modules`, build output, local data, `.env*` files and docs out of the upload.
- Each Dockerfile has a `HEALTHCHECK` on `/api/health`, which also checks the database connection.
